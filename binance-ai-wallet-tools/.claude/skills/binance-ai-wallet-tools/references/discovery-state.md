# 发现、去重与增量（给推特雷达用）

（方法参考开源项目 EZbot Grok Scout，按「会自动执行」的场景改写。）

## 搜索
- 种子词从少开始：`Binance Agent ID`、`币安 Agent ID`、`Agentic Wallet`、`AgentID`，配合动作词 mint / claim / launch / 铸造 / 领取 / 开放。中英文都搜。
- **探索和核实分开**：先用宽一点的词找线索；找到候选后，再用项目名、独特活动词、完整合约地址或已确认账号定向补查。不要一条搜索里堆满所有门槛。
- 指定账号是补充来源，不是白名单；不要只盯固定账号。
- 搜不到先换别名 / 语言 / 省略生态名的说法，不急着下结论「没有新项目」；但也不要无限换词，已有具体对象就进入研究。
- 顺着引用、父帖、官方链接追到原始来源。转发、教程、汇总只算线索；找不到原始来源就标「仅二手信息」。

## 什么算新项目 / 重要变化
- 时间窗筛的是**线索**：老项目本轮出现新活动、开放预告、实质变化，也要处理。
- 只是历史讨论或转发、没有新活动 → 不当新项目。
- 重要变化：新活动或入口开放、合约迁移、资格 / 费用 / 产物 / 退出规则变化、权限或实现变化、关键风险出现或解除、之前的缺口有了实证。
- 普通供应增长、重复宣传、热度变化不单独通知；跨过售罄 / 阶段阈值才重新判断。
- 早期项目缺官网、没合约、没开 mint 不自动淘汰：标「预告 / 待核实」，写清缺什么。

## 去重与状态（`data/radar-state.json`）
- 分开记：**来源**（推文 ID、作者、发布时间、我们首次看到的时间）、**项目**（稳定 id、官网、官推）、**活动**（链、合约及角色、阶段）。
- 同链同合约且角色相符才合并；同名、同推广者、同支付币、同注册表 / 工厂都不够。
- 保留**最早实际观察时间**；推文发布时间、代码核对时间、状态读取时间分别记。
- 只有真正成功取回并保存的时间段才推进「已检查到」；失败的时间段保留下次补查。每轮和上轮**重叠 10 分钟**，防止索引延迟漏推文。
- 通知只比较实质内容；时间戳、点赞数、重复宣传不触发重复通知。已结束的项目不反复研究，除非重新开放或出新活动。
- 资料不足的对象记下待补问题，下轮补，不要让同一个失败对象占满每一轮。
- 雷达脚本自动过滤：合约或官网已在 `projects.json` / `watch.json` 里的不再提醒；`watchAccounts` 官推里 `@别人` 开头的回复不算动态；一帖列出超过 `maxCasPerTweet` 个合约的清单帖直接丢弃；`config.radar.ignoreCas` / `ignoreDomains` 是公共合约和非项目网站。
- 钱包 BNB 低于 `config.alerts.lowBnb` 时，雷达每轮写 `ERR LOWBNB`，看板 gas 卡片标红。
- 等用户决定的事项只放看板「待你确认」区，不在对话里每次重复。

## 输出节奏
- 定时轮次没有新项目、没有重要变化：**静默**，不发空消息。
- 搜索失败或中断：如实说「本轮未完成」，不能说成「搜完了、没有新项目」。
